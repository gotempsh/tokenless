| Command | What it does |
|---|---|
| `tokenless serve` | Run the control plane (console, management API and node API) and a proxy for this machine. See [Deploy](./deploy.mdx). |
| `tokenless status` | What is set up here and the command to run next. Start here. |
| `tokenless vault list`, `service list`, `bundle list` | What you can see in the console's Vaults, Services and Access bundles pages, as a table or `--json`. |
| `tokenless session list` | Sessions, newest first: the active ones, or every one with `--all`. |
| `tokenless proxy list` | Proxies, and whether each is connected. Admins only. |
| `tokenless login`, `logout` | Sign in to the control plane; the session is kept in the OS keychain. See [Set up from the terminal](./terminal.mdx). |
| `tokenless sign-ins list`, `revoke` | The browsers and CLI logins signed in as you, and ending one or all but this one. Admins sign someone out everywhere with `--user`. |
| `tokenless service add` | Store a credential from a template, with a rule and an access bundle. |
| `tokenless service templates` | Find a template by name, host or variable. |
| `tokenless proxy add` | Create a join token and enrol this machine as a proxy. |
| `tokenless admin reset-password` | On the server's host: replace a lost password. |
| `tokenless admin rotate-root-key` | On the server's host: replace the root key. |
| `tokenless node join` | Enrol this machine as a proxy with a one-time join token. |
| `tokenless node run` | Run the proxy and the MCP gateway. |
| `tokenless run` | Run a command behind a session from an access bundle. See [Run an agent](./agents.mdx). |
| `tokenless exec` | `run`, with environment variables filled by reference. See [Placeholders](./placeholders.mdx). |
| `tokenless session start` | Open a session port for agents you start yourself. |
| `tokenless session create` | Mint a session and print its token. |
| `tokenless session info` | Show what a session can reach and the placeholders it accepts. |
| `tokenless session revoke` | End a session. |
| `tokenless mcp` | Print MCP client configuration for a bundle's MCP servers. See [MCP](./mcp.mdx). |
| `tokenless skill` | Print or install the agent skill. |
| `tokenless update` | Replace this binary with the latest release. See [Install → Update](./install.mdx#update). |

## `serve`

| Option | Default | |
|---|---|---|
| `--data-dir` | `./data` | SQLite database, and `root.key` when none is supplied |
| `--root-key-file` | `TOKENLESS_ROOT_KEY_FILE`; or the key itself in `TOKENLESS_ROOT_KEY` | The root key, kept outside the data directory. See [Deploy → The root key](./deploy.mdx#the-root-key) |
| `--database-url` | `sqlite://<data-dir>/broker.db` | |
| `--api-listen` | `127.0.0.1:8080` | Console and management API |
| `--api-tls-cert`, `--api-tls-key` | | Serve the API over HTTPS; reloaded on change |
| `--node-listen` | `127.0.0.1:8443` | Node API (mutual TLS) |
| `--node-api-name` | `localhost`, `127.0.0.1` | Names in the node API certificate (repeatable) |
| `--validation-ca` | | Extra CAs for credential tests (repeatable) |
| `--lease-secs` | `60` | How long a proxy may run without reaching the control plane |
| `--ui-dir` | | Serve the console from a directory instead of the built-in one |
| `--no-proxy` | `TOKENLESS_NO_BUILTIN_PROXY` | Don't run the built-in proxy, for a server whose proxies run on other machines. The container image sets the variable |
| `--proxy-listen` | `127.0.0.1:3128` | The built-in proxy's listener |
| `--proxy-mcp-listen` | `127.0.0.1:3129` | The built-in proxy's MCP gateway |

The built-in proxy enrols with the server on its first start, keeps its
identity in `<data-dir>/builtin-proxy.json` and shows under **Proxies** as
*built-in (this server)*. If its port is taken, `serve` says so and runs
without it. Revoked in the console, it stays off until you delete
`builtin-proxy.json`.

`serve` sends its logs to OpenTelemetry when `OTEL_EXPORTER_OTLP_ENDPOINT`
is set. See [Deploy → OpenTelemetry](./deploy.mdx#opentelemetry).

## `service add <template>`

| Option | Default | |
|---|---|---|
| `--vault` | `default` | Created when missing |
| `--bundle` | | Access bundle to add the rule to, created when missing |
| `--name` | the template's ID | Credential name |
| `--read-only` | | Rule allows only `GET` and `HEAD` |
| `--secret-file [PATH]` | `~/.tokenless/incoming/<template>` | Wait for the credential to be saved in this file (created, mode 0600); delete it once the credential is stored, keep it if storing fails; a file that was already there is never deleted otherwise |
| `--web` | | Print the console page that adds it and wait until it is saved there. Not with `--name` or `--read-only` |
| `--open` | | Open the page in the browser, or the file in the text editor |
| `--wait` | `15m` | How long `--secret-file` and `--web` wait |
| `--no-wait` | | With `--web`, only print the page |
| `--json` | | Print the service, vault and the bundle it joined (`null` if none) as JSON |

The template is matched by ID or name. A single-field credential can be
piped in on standard input. See
[Without typing the key here](./terminal.mdx#without-typing-the-key-here).

## `service templates [query]`

Lists the templates whose ID, name, alias, host or variable (`OPENAI_API_KEY`)
matches, best first; all of them without a query. Signed in, it lists the
control plane's templates, imported ones included; otherwise the built-in
ones. `--json` adds each template's fields. Exits 1 when nothing matches.

## `status`

| Option | Default | |
|---|---|---|
| `--server` | `http://127.0.0.1:8080` | The control plane to check |
| `--json` | | The report as JSON: `ready`, each check's `state` and `fix`, and `next` |

Exits 0 when agents can be started behind tokenless, 1 otherwise. For
an admin it also says whether [other hosts](./settings.mdx#other-hosts)
are blocked; allowed is flagged as a recommendation, and never stops it
being ready.

## `vault list`, `service list`, `bundle list`, `session list`, `proxy list`

Each prints a table, or the same rows as JSON with `--json` (`[]` when
there are none). They need `tokenless login`, not an API key, and show
what the console shows the person signed in; no secret is ever printed.
They read no `TOKENLESS_VAULT` or `TOKENLESS_BUNDLE`: without the flags
they list every vault you can see.

| Option | Default | |
|---|---|---|
| `--vault` (`service`, `bundle`, `session`) | every vault you can see | One vault, by name or id |
| `--bundle` (`session`) | | Only sessions minted from this access bundle, by name or id |
| `--all` (`session`) | | Include sessions that expired or were revoked |
| `--limit` (`session`) | `20` | How many to show at most, newest first |
| `--json` | | The rows as JSON |

`service list` shows each service's template, the hosts it reaches and
when its secret expires. A service whose template version is no longer
approved reaches nothing, and the list says so. `bundle list` shows the
services each bundle's rules reach. `session list` gives the ID that
`session revoke --id` takes.

## `bundle key add <bundle>`, `bundle key list`, `bundle key revoke <key>`

Launcher keys: what an agent machine starts its sessions with instead of
someone's sign-in. A key only starts sessions from its bundle, with its
limits ([Automation → Launcher keys](./automation.mdx#launcher-keys)).
`add` prints the key alone on stdout, shown only once, and how to use it on
stderr. `revoke` takes the key's name, prefix or id, and also ends the live
sessions the key started.

| Option | Default | |
|---|---|---|
| `--vault` | the only vault | By name or id |
| `--name` (`add`) | | What the key is for, such as the machine it goes on |
| `--ttl` (`add`) | `15m` | The longest session the key starts |
| `--request-limit` (`add`) | | Requests each session may make |
| `--proxy` (`add`) | | Only this proxy accepts the key's sessions; needs the right to manage proxies |
| `--label` (`add`) | | Stamped on every session the key starts, as key=value (repeatable) |
| `--expires-in-days` (`add`) | `90` | At most 365 |
| `--bundle` (`list`) | | Only this bundle's keys |
| `--json` (`list`) | | The rows as JSON |

## `sign-ins list`, `sign-ins revoke`

Where you're signed in: each browser and `tokenless login`, with the client
and when it was last used. `revoke` ends one by its id (the first
characters `list` shows are enough), every one but this one with
`--others`, or, for an admin, every one of a person's with
`--user <username>`. To end this one, use `tokenless logout`. Agent
sessions already started keep running until they expire; end them with
`tokenless session revoke`.

| Option | Default | |
|---|---|---|
| `--user` | you | Someone else's sign-ins, by username. Admins only |
| `--others` (`revoke`) | | Every sign-in of yours but this one |
| `--json` (`list`) | | The rows as JSON |

## `alerts list`, `alerts ack`

The [alerts](./console/alerts.mdx) nobody has acknowledged yet, newest
first: a session that sent a tripwire, was cut off, refused often or used
through a second proxy.
`ack` marks one looked at by its id (the first characters `list` shows
are enough).

| Option | Default | |
|---|---|---|
| `--all` (`list`) | | The acknowledged ones too |
| `--json` (`list`) | | Every one as JSON; the table shows the newest 50 |

## `tripwire add`, `tripwire list`, `tripwire remove`

[Tripwires](./console/vaults.mdx#tripwires): fake keys to plant on an
agent's machine. `add` creates one and prints it once, ready to append
to a file; how else to plant it goes to stderr. When the AWS credentials
file on the machine you run it on has a `[default]` profile already, an
AWS decoy is printed as a profile named after the tripwire (with a
number added if the file has that name too), so appending it doesn't
break the file. `list` shows each one's
first characters and when it was last tripped. `remove` deletes one by
name, the start `list` shows, or id.

```sh
tokenless tripwire add --kind aws --name build-runner >> ~/.aws/credentials
tokenless tripwire add --kind github --name laptop --vault work >> .env.local
```

| Option | Default | |
|---|---|---|
| `--kind` (`add`) | | `aws`, `github`, `openai` or `generic` |
| `--name` (`add`) | | Where it is planted, such as the machine's name |
| `--vault` | the only one | The vault, when there is more than one |
| `--json` (`list`) | | The rows as JSON |

## Client commands

`login`, `vault`, `service`, `bundle`, `proxy`, `run`, `exec`, `session` and `mcp` take `--server`; `run`, `exec`, `mcp` and the `session` commands other than `session list` also take the rest. Without an API key they use the session from `tokenless login`. The `list` commands only use that sign-in, and take `--vault` and `--bundle` as flags only: `TOKENLESS_VAULT` and `TOKENLESS_BUNDLE` do not narrow them.

| Flag | Environment | Default |
|---|---|---|
| `--server` | `TOKENLESS_URL` | `http://127.0.0.1:8080` |
| `--api-key-file` | `TOKENLESS_API_KEY` (the key itself) | |
| `--vault` | `TOKENLESS_VAULT` | the API key's vault |
| `--bundle` | `TOKENLESS_BUNDLE` | |
| `--session-token-file` (`run`, `exec`, `session start`, `session revoke`) | `TOKENLESS_SESSION_TOKEN` (the token itself) | used when no bundle is given |
| `--name` (when minting) | | the session's name on the Sessions page |
| `--proxy` | `TOKENLESS_PROXY_ADDRESS` | `127.0.0.1:3128` |
| `--no-skill-hint` (`run`) | `TOKENLESS_NO_SKILL_HINT` | off: `run -- claude` says when the skill isn't installed |
| `--no-port-password` (`run`, `exec`, `session start`) | | off: the session port refuses clients without the password it puts in `HTTPS_PROXY`. Only for a client that can't send proxy credentials: any program on the machine can then use the session |

Inside `run` or behind `session start`, `TOKENLESS_PROXY` is set to the
session port and `HTTPS_PROXY` points at it.
