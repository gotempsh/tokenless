Everything in the [Quickstart](./quickstart.mdx) can be done without the
console: sign in, add a service and enrol a proxy.

## Where you are

```sh
tokenless status
```

It checks the control plane, your sign-in, the services, the proxy and the
agent skill, and ends with the one command to run next. It exits 0 once
agents can be started behind tokenless, 1 before. `--json` gives an agent
the same report, with `next` holding that command.

## Sign in

```sh
tokenless login                 # the admin printed by `tokenless serve`
```

It asks for the password, and an authenticator code if the account has
one. People who sign in to the console with
[single sign-on](./settings.mdx#single-sign-on) have no password here; in a
terminal they use a session token from an access bundle's page, or an API
key from an admin. The session is kept in the operating system's keychain (macOS
Keychain, Windows Credential Manager, the Linux kernel keyring) and lasts
as long as a console session. `--server` signs in to another control
plane; `tokenless logout` ends the session.

Where there is no usable keychain, for example in a Docker container
(its default security profile blocks the kernel keyring), the session
goes to `~/.config/tokenless/sessions/` instead, in a file only you can
read, and `login` says so. The Linux kernel keyring also forgets
everything on reboot; sign in again then.

On macOS the binary is not notarized, so after installing or upgrading it
the Keychain asks once whether `tokenless` may read its entry. Choose
**Always Allow**.

## Add a service

```sh
tokenless service add github --vault work --bundle code-review
```

It asks for the token without echoing it, or reads it from standard input
when piped (`gh auth token | tokenless service add github ...`). Then it:

1. creates the vault if it doesn't exist,
2. stores the credential, encrypted, write-only from then on,
3. adds a rule that lets agents use it with the template's scope
   (`--read-only` limits it to `GET` and `HEAD`),
4. adds that rule to the bundle, creating the bundle if needed.

Templates with several fields (a client ID and a secret, say) ask for
each one, so run those in a terminal. `--name` names the credential when
the vault already has one for the same service.

To find a template's ID, search by name, host or the variable a tool reads
its key from. It lists the built-in templates before you sign in, and
your control plane's afterwards:

```sh
tokenless service templates OPENAI_API_KEY
```

### Without typing the key here

When an agent sets tokenless up for you, it runs `service add` with one of
these, so the key goes from you to tokenless and never through the agent:

```sh
tokenless service add openai --vault personal --bundle my-agent --secret-file --open
tokenless service add openai --vault personal --bundle my-agent --web --open
```

- `--secret-file` creates `~/.tokenless/incoming/<template>` (or the path
  you give it), readable only by you, and waits until you save the key in
  it. Then it stores the key and overwrites and deletes the file. If
  storing fails before the key is saved (a sign-in that ended, a name
  already taken), the file stays and running the command again reads it;
  if the key was saved but its rule or bundle was not, the file is deleted
  and the error says to finish the service on the vault's page. A key
  written as `OPENAI_API_KEY=sk-...` is stored without the name. A template
  with several fields gets a line per field; a line it can't read is
  reported and it keeps waiting for the fix. A file it created is deleted
  if the command is stopped or gives up waiting; a file that was already
  there is left as it was. `--open` opens it in your text editor;
  close the editor once you have saved, as some keep a backup copy.
- `--web` prints the console page that adds the service, with the vault
  and bundle chosen when they exist, and waits until you save it there.
  `--open` opens it in your browser. `--no-wait` only prints the page.

Both wait up to 15 minutes (`--wait 30m` for longer), and `--json` prints
the service, its vault and the bundle it joined (`null` if none, for a
service saved on the page without one) when it is done.

## Enrol a proxy

```sh
tokenless proxy add --name laptop     # writes ./node.json
tokenless node run
```

`proxy add` creates a join token and enrols this machine with it in one
step. It reaches the node API on the control plane's host at port 8443;
pass `--control-url` when it listens elsewhere. The node API's certificate
names `localhost` and `127.0.0.1` unless `tokenless serve` was started
with `--node-api-name <host>`, so a proxy on another machine needs the
control plane started with the name it dials.

`tokenless run` checks that a proxy is answering before it starts the
agent, and says so when none is.

## Run an agent

```sh
tokenless run --vault work --bundle code-review -- claude
```

Signed in, `run`, `exec`, `session` and `mcp` mint sessions with your
account, so you don't need an API key on your own machine. Use an API key
for CI and other unattended runs; see
[Automation and API keys](./automation.mdx).

## Sensitive actions

With an authenticator, adding credentials and rules needs a code from the
last five minutes; signing in counts. When the server asks for a newer
one, the commands prompt for it and carry on.

## A lost admin password

On the machine that runs the control plane, against the same data:

```sh
tokenless admin reset-password --data-dir ./tokenless-data
```

It prints a new password once and ends every session of that account.
It works while the server is running. With PostgreSQL, pass
`--database-url` as well. For the container image:

```sh
docker exec tokenless tokenless admin reset-password --data-dir /data
```
